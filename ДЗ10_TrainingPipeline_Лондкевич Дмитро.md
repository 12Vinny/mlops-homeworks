## 1. High-level workflow automated training pipeline

Процес автоматизованого тренування моделі — це керований workflow, який забезпечує відтворюваність, безпеку та прозорість створення нових ML-моделей. Високорівнева схема цього процесу виглядає наступним чином:

`GitLab event / manual trigger` ➔ `GitLab CI pipeline` ➔ `AWS Step Functions execution` ➔ `Data validation` ➔ `Training job` ➔ `Model evaluation` ➔ `Logging metrics and artifacts` ➔ `Model Registry update` ➔ `Notification to team`

**Опис етапів та логіки процесу:**
* **Що запускає pipeline:** Процес ініціюється певним тригером у GitLab, яким може бути злиття коду в головну гілку (merge into main), ручний запуск інженером (manual trigger) або запланований запуск за розкладом (schedule).
* **Роль GitLab CI:** GitLab CI виступає первинним оркестратором, який валідує Git-контекст (commit SHA, гілка), автентифікується в AWS із дотриманням принципу найменших привілеїв та передає команду на запуск хмарного workflow, не виконуючи важких обчислень самостійно.
* **Роль AWS Step Functions:** Цей сервіс відповідає за безпосереднє виконання кроків машинного навчання (перевірка даних, запуск тренування на AWS SageMaker чи EC2, обчислення метрик), забезпечуючи надійне управління станами, паралелізм та стійкість до збоїв.
* **Де фіксуються результати:** Усі параметри експерименту, метрики та самі артефакти моделі автоматично логуються у спеціалізованій системі трекінгу,наприклад, MLflow.
* **Де зберігається кандидат:** Якщо модель успішно проходить базові перевірки, вона зберігається та отримує статус "Candidate" у Model Registry, очікуючи на подальше рішення щодо релізу.
* **Хто отримує повідомлення:** Після завершення пайплайну (успішного чи з помилкою), інтегрована система сповіщень надсилає детальне повідомлення в робочий месенджер (наприклад, Slack) відповідальній команді, AI PM та Tech Lead-у для прийняття подальших рішень.

## 2. Контрольні точки pipeline

Для того щоб автоматизація не призвела до неконтрольованого створення неякісних моделей, ми впроваджуємо чіткі контрольні точки на кожному етапі пайплайну.

| Етап pipeline | Що перевіряє команда | Хто owner | Що є успіхом | Що робити при помилці |
| :--- | :--- | :--- | :--- | :--- |
| **Data validation** | Наявність актуальних даних, відповідність схеми, заповненість обов'язкових полів. | Data Engineer | Дані пройшли перевірку, аномалій не виявлено. | Зупинити pipeline, надіслати алерт Data-команді для виправлення датасету. |
| **Training job** | Запуск тренування з правильною версією коду, використання відповідних обчислювальних ресурсів (GPU/CPU). | AI/ML Engineer | Тренування успішно завершилося без технічних збоїв чи нестачі пам'яті (OOM). | Перевірити інфраструктурні логи, за необхідності збільшити ресурси або створити incident-тікет. |
| **Model evaluation** | Розрахунок ключових ML-метрик на тестовій вибірці та їх порівняння з baseline. | AI/ML Engineer + AI PM | Метрики нової моделі перевищують встановлений поріг (threshold). | Зупинити просування моделі, зберегти логи для аналізу та сповістити команду про деградацію якості. |
| **Logging metrics & artifacts** | Коректність збереження гіперпараметрів, метрик та файлів самої моделі у системі трекінгу. | MLOps Engineer | Усі артефакти та метрики прив'язані до правильного `run_id` у MLflow. | Перевірити конфігурацію підключення до MLflow/S3 та перезапустити етап логування. |
| **Model Registry** | Присвоєння моделі правильного статусу, версії та відповідних метаданих. | MLOps Engineer | Модель успішно зареєстрована в реєстрі зі статусом "Candidate" (або "Staging"). | Вручну перевірити логіку Model Registry API та виправити конфлікт версій. |
| **Notification** | Формування та доставка повідомлення з контекстом виконання до правильного каналу зв'язку. | AI PM / MLOps Engineer | Команда отримала зрозуміле повідомлення в Slack із посиланням на результати. | Додати fallback-механізм (наприклад, Email) та перевірити налаштування вебхуків. |

## 3. Quality gates для нової моделі

Успішне завершення технічного процесу тренування моделі (наприклад, скрипт відпрацював без помилок і згенерував артефакт) ще не означає, що цю модель можна випускати до користувачів. Щоб стати кандидатом на release, нова модель повинна пройти через серію жорстких перевірок — Quality Gates. Ці контрольні точки гарантують, що ML-рішення не лише технічно працездатне, але й відповідає бізнес-вимогам та перевищує поточні стандарти якості. Якщо модель не проходить хоча б один із цих гейтів, її просування автоматично блокується, навіть якщо технічний пайплайн світиться зеленим.

| Quality gate | Приклад правила | Хто перевіряє | Рішення |
| :--- | :--- | :--- | :--- |
| **Data quality** | Немає критичних schema errors, відсутні пропуски в ключових фічах, розподіл даних відповідає очікуванням. | Data Engineer | Продовжити або зупинити pipeline для очищення даних. |
| **Model metric** | F1-score або Accuracy нової моделі не нижче поточного production baseline + мінімальний threshold (наприклад, +1%). | AI/ML Engineer | Продовжити процес реєстрації або rejected (відхилити модель). |
| **Business metric** | Немає погіршення якості прогнозів на ключовому, найбільш прибутковому сегменті користувачів; Latency (час відповіді) залишається в межах SLA. | AI PM | Погодити просування кандидата або повернути на додатковий аналіз. |
| **Approval** | Модель має статус "approved" після перевірки результатів та ризиків людиною (Manual Approval), що блокує неконтрольований випуск. | AI PM / Tech Lead | Дозволити розгортання в staging або production середовищах. |

## 4. Правила запуску training pipeline

Автоматизація тренування вимагає чітко встановлених правил щодо того, коли саме має стартувати пайплайн. Оскільки запуск AWS Step Functions та використання обчислювальних ресурсів коштує грошей, кожен тригер має бути обґрунтованим. Нижче наведено розширений аналіз можливих сценаріїв запуску та їх доречність для різних середовищ.

| Trigger | Коли доречний | Перевага | Ризик | Рекомендоване середовище |
| :--- | :--- | :--- | :--- | :--- |
| **Push у main** | Навчальний або dev-сценарій, коли інженери активно експериментують з кодом. | Простий запуск, що дозволяє миттєво перевірити вплив змін на пайплайн. | Може створювати зайві training runs та випалювати хмарний бюджет при дрібних комітах. | dev |
| **Manual trigger** | Коли потрібен суворий людський контроль перед фінальним тренуванням кандидата на реліз. | Менше випадкових запусків, максимальна контрольованість витрат. | Залежить від дисципліни команди; можна просто забути запустити тренування. | staging / prod |
| **Schedule (За розкладом)** | Регулярний retraining (наприклад, щонеділі вночі), коли нові дані надходять стабільно й прогнозовано. | Висока передбачуваність процесу, знімає рутину з команди. | Може тренувати модель без реальної потреби (якщо нових даних мало або вони не змінилися), даремно витрачаючи ресурси. | staging / prod |
| **Зміна model config** | Коли дата-саєнтисти оновлюють лише гіперпараметри або архітектуру в конфігураційному файлі. | Тренування стартує лише при свідомій зміні параметрів, відсікаючи запуски через правки у README чи CI-скриптах. | Може виникнути розсинхрон, якщо конфіг вже змінили, а нові дані для нього ще не підготували. | dev / staging |
| **Drift signal** | Реакція на деградацію якості моделі (Model Drift) або зміну у вхідних даних (Data Drift) у production. | Запуск відбувається виключно за реальною потребою; гарантує актуальність моделі. | Потрібен дуже зрілий та дорогий monitoring; хибні алерти можуть запустити нескінченний цикл перенавчань. | prod |

Отже, правила запуску мають бути узгоджені на рівні архітектури проєкту. Частий автоматичний запуск (Push) створює гнучкість, але генерує зайві витрати, тому він підходить лише для Dev. Для Production-середовища найкраще комбінувати тригери: використовувати Schedule для рутинного оновлення моделей зі стабільним потоком даних, а Manual або Drift signal — для складних систем, де перенавчання має бути жорстко обґрунтованим або контрольованим.

## 5. Risk assessment (Risk Register)

Інтеграція GitLab CI з AWS Step Functions створює потужний автоматизований механізм, проте вимагає суворого контролю безпеки та витрат. Нижче наведено реєстр із 7 ключових ризиків та заходів щодо їх мінімізації до запуску пайплайну в production.

| Ризик | Ймовірність | Вплив | Як зменшити ризик | Owner |
| :--- | :--- | :--- | :--- | :--- |
| **GitLab CI має надмірні AWS-права** | Medium | High | Використовувати OIDC-автентифікацію замість статичних ключів; налаштувати IAM-ролі за принципом найменших привілеїв (Least privilege) окремо для dev, staging та prod. | DevOps / MLOps |
| **Training запускається занадто часто** | High | Medium | Налаштувати правила запуску: manual trigger для prod/staging, запуск за розкладом, або тригер лише при зміні файлів конфігурації моделі/даних. | AI PM |
| **Модель не проходить quality gates, але йде далі** | Medium | High | Зробити Quality Gates жорстким блокером у пайплайні (hard stop). Обов'язкове порівняння з baseline; заборона просування без manual approval. | AI/ML Engineer + AI PM |
| **Step Functions падає без сповіщення команди** | Medium | High | Додати `Catch` блок у конфігурацію Step Functions, який гарантовано відправляє failure-статус та лог помилки через SNS/Lambda у робочий месенджер команди. | MLOps Engineer |
| **Пропуск етапу Data Validation** | Low | High | Архітектурно закріпити крок перевірки даних як перший обов'язковий етап Step Functions; пайплайн повинен падати, якщо валідація не пройдена або схема не знайдена. | Data Engineer |
| **Помилка логування (MLflow недоступний)** | Low | High | Налаштувати механізм retry (повторних спроб) для підключення до MLflow. Якщо логування остаточно не вдається, вважати весь training job неуспішним. | MLOps Engineer |
| **Автоматичний реліз у Production без перевірки** | Low | Critical | Фізично розділити Training Pipeline та Deployment Pipeline. Унеможливити автоматичний deploy в production без явного кроку "Manual Approval" у GitLab CI. | Tech Lead |

## 6. Acceptance criteria для Jira-задачі

Для того щоб команда розробки чітко розуміла вимоги до створення пайплайну, задачу **“Інтегрувати GitLab CI з AWS Step Functions для automated training pipeline”** описано через детальні Acceptance Criteria (AC). Задача вважається виконаною лише тоді, коли продукт відповідає всім наведеним нижче пунктам.

**Acceptance Criteria:**
* **Trigger & Security:** GitLab CI pipeline успішно запускає AWS Step Functions workflow. Доступ GitLab CI до AWS налаштований безпечно (через OIDC або IAM Roles), без надання надмірних адміністративних прав.
* **Git-контекст:** У вхідні параметри (input) Step Functions коректно передаються метадані Git-репозиторію: `commit SHA`, `branch`, та `source="gitlab-ci"`.
* **Visibility:** Step Functions execution чітко видно в AWS Console, а його ідентифікатор (ARN) логується у консолі GitLab CI для швидкого переходу та дебагінгу.
* **Data Validation:** Pipeline містить окремий обов'язковий крок `Data validation`, який виконується строго перед початком training job.
* **Logging:** Усі ключові результати тренування (ML-метрики, гіперпараметри) та артефакти моделі автоматично логуються в системі трекінгу (наприклад, MLflow).
* **Quality Gates:** Pipeline автоматично перевіряє метрики нової моделі на відповідність Quality Gates (наприклад, порівняння з baseline). Якщо метрики гірші за поріг, пайплайн переривається.
* **Model Registry:** При успішному проходженні Quality Gates нова модель автоматично отримує відповідний статус (наприклад, "Candidate" або "Staged") у Model Registry.
* **Production Control:** Архітектура містить жорстку заборону автоматичного production-релізу; перехід моделі у production неможливий без кроку manual approval.
* **Notification:** Команда отримує автоматичне notification (наприклад, у Slack) про `success` або `failure` пайплайну з деталями статусу, лінком на виконання та інформацією про Git-контекст.

## 7. Notification messages

Сповіщення (notification) — це критичний елемент керованого пайплайну. Воно не просто констатує факт завершення роботи, а дає команді необхідний контекст для розуміння статусу, містить посилання для швидкого розслідування та чітко визначає наступні кроки.

**Приклад повідомлення при успішному виконанні:**

✅ **Training pipeline completed successfully**

*   **Model:** `churn_prediction_v3`
*   **Source:** GitLab CI
*   **Commit:** `a1b2c3d` (branch: `feature/new-features`)
*   **Step Functions execution:** `MLOpsPipeline / execution-123`
*   **Metrics:** F1-score = 0.83, Recall = 0.79 (перевищує baseline)
*   **Status:** Candidate registered
*   **Details:** [Link to MLflow run] / [Link to Model Registry]
*   **Next action:** Tech Lead reviews quality gates before release decision.
*   **Owner:** Tech Lead

**Приклад повідомлення при помилці:**

❌ **Training pipeline failed**

*   **Model:** `churn_prediction_v3`
*   **Source:** GitLab CI
*   **Commit:** `a1b2c3d` (branch: `feature/new-features`)
*   **Failed step:** `DataValidation`
*   **Reason:** Missing required column `customer_age` in the input dataset.
*   **Details:** [Link to Step Functions execution logs] / [Link to GitLab job logs]
*   **Next action:** Data Engineer checks dataset and restarts pipeline after fix.
*   **Owner:** Data Engineer

## 8. Короткий висновок

Впровадження automated training pipeline є фундаментальним кроком у MLOps, оскільки воно перетворює непередбачувані, ручні експерименти на стабільний та керований бізнес-процес. У цій архітектурі GitLab CI виступає як надійний ініціатор та контролер версій (Git-контекст), тоді як AWS Step Functions бере на себе важку роботу з оркестрації обчислень, логування та валідації. Водночас важливо розуміти, що технічний success пайплайну (відсутність помилок у коді) зовсім не означає готовності моделі до production. Саме для цього ми впроваджуємо Quality Gates та чіткі правила запуску. Лише після того, як модель доведе свою перевагу над baseline, пройде бізнес-валідацію та отримає manual approval від відповідальних осіб (Tech Lead / AI PM), її можна розглядати як надійне рішення для інтеграції в кінцевий продукт.
