## 1. Бізнес-контекст ML-задачі

У рамках цього проєкту наша технічна команда розробляє модель для автоматичної класифікації трьох видів ірисів (setosa, versicolor, virginica) на основі чотирьох фізичних характеристик квітки: довжини та ширини чашолистка і пелюстки. У реальному бізнес-середовищі, наприклад, в агропромисловому комплексі або системах розумних теплиць, така система комп'ютерного зору чи сенсорного аналізу дозволяє автоматизувати процес сортування рослин, суттєво зменшуючи потребу в ручній праці та мінімізуючи людський фактор. 

Оскільки класи в оригінальному датасеті Iris повністю збалансовані, а саме по 50 екземплярів кожного виду, тоді головною бізнес-метрикою для нас є загальна частка правильних відповідей, адже помилка на будь-якому з видів має для нас однакову вартість. Водночас для розуміння надійності моделі перед запуском у production ми обов'язково маємо враховувати функцію втрат, яка суворо штрафує алгоритм за впевнені, але помилкові передбачення. Якщо модель буде класифікувати квіти неправильно і з високою впевненістю, це може призвести до системних помилок у пакуванні та репутаційних втрат. Тому нам потрібен алгоритм, який демонструє не лише високу точність, але й високий рівень загальної впевненості у своїх прогнозах.

## 3. Визначення кандидата на staging / production

На основі проаналізованих запусків найкращим кандидатом для переходу в наступне середовище (staging) є run **`rf-depth3`**. 

**Обґрунтування вибору:**
* **Перевага над baseline:** Цей запуск використовує алгоритм `random_forest` і демонструє суттєве покращення порівняно з базовою моделлю (`logreg-baseline`). Точність зросла з 0.933 до 0.956, а ключовий для надійності показник Loss впав із 0.191 до 0.141. Це означає, що модель не лише частіше вгадує правильний клас, але й робить це з більшою впевненістю.
* **Відсутність trade-off:** Нам не довелося жертвувати однією метрикою заради іншої. Ми бачимо одночасне покращення як Accuracy, так і Loss.
* **Наявність артефактів (Production-readiness):** Найголовніша причина вибору полягає в тому, що `rf-depth3` — це єдиний запуск, для якого інженери коректно зберегли `model artifact`. У репозиторії MLflow присутня папка `model` з файлами `MLmodel`, `model.skops`, `conda.yaml` та `requirements.txt`. Без цих файлів будь-які, навіть найвищі метрики (як у `rf-small`), є безглуздими для бізнесу, оскільки їх неможливо розгорнути в production чи відтворити в іншому середовищі. 

Таким чином, завдяки наявності повного пакета для відтворення та найкращим бізнес-метрикам, саме `rf-depth3` є єдиним валідним кандидатом.

## 4. Перевірка Grafana / Prometheus метрик

Щоб переконатися у стабільності операційного моніторингу, ми проаналізували експортовані метрики `mlflow_accuracy` та `mlflow_loss` в інтерфейсі Prometheus. 

**Grafana / Prometheus показує:**
* Обидві ключові метрики (`mlflow_accuracy` та `mlflow_loss`) успішно збираються і доступні для візуалізації як у вигляді графіків, так і в табличному форматі. 
* Кожна метрика має вичерпний набір лейблів: `experiment`, `model_type`, `run_name` та унікальний `run_id`, що дозволяє чітко ідентифікувати, якій саме моделі належать результати.
* На графіках дійсно присутній розрив близько 08:34 (UTC), який, як підтверджено командою, був спричинений перезапуском exporter-а. Проте, оскільки значення метрик після перезапуску не змінилися, це не впливає на загальну оцінку моделей.

**MLflow UI показує:**
* Ті самі значення Accuracy та Loss. Дані в Prometheus повністю збігаються з даними в MLflow, наприклад, для `rf-depth3` Accuracy становить 0.9555, а Loss — 0.1414 в обох системах.

**Разом ці інструменти допомагають:**
* MLflow виступає як Source of Truth для дата-саєнтистів під час розробки, тоді як Prometheus/Grafana дозволяють DevOps та MLOps інженерам будувати оперативні дашборди і налаштовувати алерти, наприклад, якщо нова розгорнута модель раптово покаже деградацію Accuracy нижче baseline. Завдяки міткам `run_id` ми можемо швидко зіставити графік із конкретним збереженим артефактом.

**Але для production-рішення ще бракує:**
* Інформації про технічні метрики (CPU/RAM/Latency) під час навантаження. Самі по собі метрики MLflow у Grafana показують лише результати валідації на тестовому датасеті, але не дають розуміння, як швидко і стабільно `rf-depth3` працюватиме при обробці реальних користувацьких запитів.

## 5. Оцінка production-readiness процесу

Для прийняття рішення про розгортання ми маємо переконатися не лише у якості моделі, а й у зрілості самого MLOps-процесу. Результати аудиту процесу навколо моделі наведено нижче.

| Питання | Так / Ні / Частково | Коментар |
| :--- | :--- | :--- |
| **Є baseline для порівняння?** | Так | Run `logreg-baseline` слугує надійним орієнтиром для оцінки нових алгоритмів. |
| **Є зрозуміла головна метрика?** | Так | Для збалансованих класів обрано Accuracy та Log Loss для контролю впевненості. |
| **Є model artifact?** | Частково | Він є лише для одного запуску (`rf-depth3`), що свідчить про нестабільність процесу збереження. |
| **Є run ID для кандидата?** | Так | Кандидат зафіксований під унікальним ID `2ddc4f9d563c43e5a7c6c8523a580db3`. |
| **Є параметри експерименту?** | Так | Для кожного run зафіксовано алгоритм, `max_depth`, `random_state` тощо. |
| **Є метрики в MLflow?** | Так | Accuracy та Loss повністю трекаються. |
| **Є метрики в Grafana / Prometheus?** | Так | Експорт налаштований, дані збігаються з MLflow. |
| **Є критерій переходу в staging?** | Ні | Команді бракує чітко задокументованого порогу, наприклад, Accuracy > 0.95 та наявність артефакту. |
| **Є rollback-план?** | Ні | Відсутня інформація про те, як ми повернемося до попередньої моделі в разі збою. |
| **Є owner рішення?** | Ні | Незрозуміло, хто (DS, DevOps чи MLOps) відповідає за моніторинг моделі після релізу. |
| **Є план моніторингу після deployment?** | Частково | Інфраструктура (Prometheus) готова, але немає плану моніторингу деградації даних (Data Drift). |

## 6. Опис ризиків (Risk Register)

На основі виявлених прогалин ми сформували реєстр ключових ризиків, які потребують уваги до виходу в production.

| Ризик | Ймовірність | Вплив | Як зменшити |
| :--- | :--- | :--- | :--- |
| **Нестабільне збереження model artifact** | Висока | Критичний | Впровадити обов'язковий чекліст у CI/CD або змінити код навчання так, щоб MLflow завжди зберігав модель автоматично, наприклад, через `mlflow.autolog()`. |
| **Немає rollback-плану** | Середня | Високий | Задокументувати процедуру швидкого відкату, наприклад, через перемикання Alias або Tag в MLflow Model Registry. |
| **Не визначено ownership** | Висока | Середній | Чітко розподілити ролі: хто оплачує S3 для артефактів, хто очищає старі експерименти, хто чергує при алертах. |
| **Немає Data Drift monitoring** | Середня | Високий | Додати інструменти, наприклад, Evidently AI, для моніторингу розподілу вхідних ознак ірисів у production. |
| **Відсутність нагрузочного тестування** | Середня | Високий | Перед production розгорнути `rf-depth3` у staging та перевірити час відповіді (Latency) і споживання RAM під час обробки тисяч запитів. |

## 7. PM Decision Report

**Рекомендація:**
- **Go to staging** - передати модель у staging середовище для інтеграційних перевірок.

**Обґрунтування:**
Технічна команда успішно підготувала модель-кандидата `rf-depth3`, яка суттєво перевершує базове рішення та повністю готова до технічного розгортання завдяки збереженому артефакту.

**Основні докази:**
- Наявний чіткий baseline (`logreg-baseline`).
- Модель `rf-depth3` демонструє найвищу точність (0.956) та найнижчий loss (0.141).
- У MLflow наявний повний audit trail для цього run (ID, параметри, метрики).
- Збережено model artifact (папка `model` з `MLmodel` та залежностями).
- Операційний моніторинг (Prometheus) налаштовано та синхронізовано.

**Основні ризики:**
Процес розробки поки що виглядає ручним — артефакти зберігаються не для всіх запусків, відсутній затверджений rollback-план та не визначені власники процесів підтримки. Також ми не знаємо, як алгоритм `random_forest` поведе себе під реальним навантаженням.

**Що потрібно зробити перед production:**
1. Провести навантажувальне тестування (Load Testing) у середовищі staging.
2. Розробити та задокументувати процедуру відкату (Rollback).
3. Призначити Owner-а для моніторингу моделі та інфраструктурних витрат.
4. Впровадити політики автоматичного очищення (cleanup) старих експериментів у MLflow для оптимізації бюджету.
